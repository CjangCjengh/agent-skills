# 任务书写作与去 AI 味

- 任务书应让接收者直接看懂要做什么、基本要求是什么、需要交付什么。把任务交代清楚即可，不写成完整研究计划、操作手册或考核制度。

- 面向接收者的实际背景写作。懂大模型或编程，不等于熟悉游戏开发等具体应用。保留完成任务所需的概念，解释必要的专业内容，不默认接收者参加过前期讨论，也不写“本题取自此前研究计划”这类依赖内部背景的话。

- 先核清主要目标，再安排细节。例如，降低生成成本与降低修复成本不是同一任务。辅助步骤可以计入整体过程，但不能因其容易描述，就把辅助步骤写成任务重点。用户要设计 agent system 时，也不能缩成只改一条 prompt。

- 不擅自增加工作日、预计工时、截止时间、报告页数、实验数量、评分标准或提交清单。用户未指定的实现方式和探索空间保留给执行者，不以“建议”为名替用户创造额外要求。

- 交付材料写到足以辨认即可。用户要 GitHub 链接，就不必另列源码、目录、依赖、截图等一串附件；用户要报告和框架图，就交代用途，不自行限定页数、图数和每一节的写法。

- 用必要的少量标题组织任务、要求、交付物和资源，不强迫每份文档包含所有栏目。删去重复说明和无关背景，篇幅由内容决定，不为凑一页删掉关键信息，也不为显得完整扩成多页。

- 专业名词以接收者容易理解为准，可以直接用 prompt、agent system、technical report 等通行英文表达，不为全中文而生造译名。沿用用户已经确定的叫法，避免同一概念在文中换来换去。

- 任务书正文优先用直接、客观的要求，如“选择合适的模型”“提供代码链接”。不反复称呼接收者，不写“希望你能”“你需要认识到”等说教式句子。用户明确要求不出现某个人称时，检查全文；这种局部要求不推广到其他文体。

- 鼓励 AI 辅助时采用自然的说明，而不是授权式口吻。例如，“现在 AI 辅助编码、写作和作图已经很常见，这次任务也鼓励充分使用这些工具”，比“允许使用 AI 辅助完成上述工作”更符合协作语气。

- 直接说实际要求，少写“不是简单地……而是……”“并非盲目……”等无必要的自我辩护。检查是否为了反驳一个没人提出的误解，额外写了“此地无银三百两”式的解释。确实影响任务理解的条件与区别仍需保留。

- 不用笼统赞美代替检查。对 AI 生成的文字和图，不预设“图画得漂亮”或“内容已经完善”；具体检查语句是否多余、术语是否易懂、要求是否清楚、图中逻辑关系是否成立。

- 用户要求说明 AI 辅助过程时，让报告交代工具如何参与编码、写作或作图，以及输出如何被检查和修改。通过实际的修改前后对照说明发现的问题和处理方法，不只列工具名称，也不以“更自然、更像人写的”代替解释。

- 给思路时，尽量结合参考文献中的具体方法，简短说明可以借用哪个环节。例如，先尝试生成、失败后再规划，或在重复交互时才介入。保留“也可自行提出方法”的空间，不把参考思路写成唯一指定方案。

- 例子用于帮助理解，数量和细节以够用为准。笼统的“选择少量任务”不够清楚时，可换成具体要求或给出可选基准；已经提供适合选题的基准及入口时，不必再重复列一串例子。

- 比较要求只保留判断结果所必需的条件，如相同模型、相同任务，以及功能是否满足要求。讨论成本时讲清统计范围，避免只计算直接生成、漏掉规划和重试等额外开销。不要把这些基本要求扩成冗长的实验规程。

- 参考文献服务于任务本身。按用户要求筛选时效、发表场所及方法限制，例如近期、无需训练、可通过 API 尝试；不能只因为标题相关就推荐。简短说明可借鉴之处，不另写一篇文献综述，也不把跨场景尝试说成已经验证有效。

- 文中提到具体论文或基准时，添加对应的引用编号和完整文献信息，核实作者、标题、年份与出处。预印本按预印本引用，论文不要写成“项目主页”。项目网页可以作为资源入口，但不能替代用户明确要求的论文引用。

- 对外部资源和接口，区分“已写入文档”与“已经验证可用”。需要核验时检查真实链接或最小调用，不能仅凭地址格式、模型列表或配置存在就声称实际生成成功。将必要的使用信息写入任务书，不把排查过程整段塞入正文。

- 排版以易读、便于转发为主，避免无意义的配色、标题线、页角标签和时间标注。用户要求黑白、简洁时直接遵守，不靠更多装饰体现完成度。保留正常的字号和间距，导出后检查分页、链接与文字是否完整。

- 修改时保留已经确认的要求，按最新反馈处理对应内容，不借小改动扩写其他部分。最后从接收者角度通读，确认没有内部背景、擅加要求或重复解释，并交付实际更新后的文档。修改说明保持简短，除非用户要求，不另附长篇自查报告。
